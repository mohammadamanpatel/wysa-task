# Modular Conversation Flow Backend

A backend service that manages modular, question-based conversation flows.

A user can start a module, answer questions, move to another question, switch between modules, return to previously visited modules, and maintain complete conversation history.

## Architecture

The project follows a simple layered architecture:

```text
Request
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
MongoDB
```

### Controller

Handles HTTP requests, validates basic request data, calls the service layer, and returns the response.

### Service

Contains the main conversation flow and business logic.

### Repository

Handles database operations such as finding, creating, and updating documents.

### Model

Defines the MongoDB/Mongoose data structure.

# Data Design

The system mainly uses two collections.

## 1. Modules

The module collection stores modules and their questions.

Example:

```json
{
  "moduleId": "module-uuid",
  "name": "Career",
  "questions": [
    {
      "questionId": "question-uuid",
      "text": "What kind of help are you looking for?",
      "isCheckPoint": false,
      "options": [
        {
          "optionId": "option-uuid",
          "text": "Backend Development",
          "nextModuleId": "career-module-uuid",
          "nextQuestionId": "question-uuid"
        }
      ]
    }
  ]
}
```

Each question contains:

- `questionId`
- `text`
- `isCheckPoint`
- `options`

Each option contains:

- `optionId`
- `text`
- `nextModuleId`
- `nextQuestionId`

Question IDs and option IDs are generated by the backend using UUIDs.

## 2. User Conversation

The user conversation collection stores the user's conversation history and current state.

It contains:

```text
conversationHistory
activeState
moduleStates
```

### Conversation History

Stores every answer given by the user.

Example:

```json
{
  "moduleId": "career-module-id",
  "questionId": "question-id",
  "optionId": "option-id",
  "contextVersion": 1,
  "answeredAt": "timestamp"
}
```

History is preserved even when the user moves to another module.

### Active State

Stores where the user is currently located.

Example:

```json
{
  "moduleId": "finance-module-id",
  "currentQuestionId": "finance-question-id"
}
```

### Module States

Stores the user's state for individual modules.

This allows the user to return to a previously visited module while keeping its saved state.

Each module state contains:

```json
{
  "moduleId": "module-id",
  "currentQuestionId": "question-id",
  "contextVersion": 1
}
```

---

# Context Version and Checkpoints

Some questions are marked as checkpoints using:

```json
"isCheckPoint": true
```

When the user answers a checkpoint question, the context version for that module is increased.

For example:

```text
Before checkpoint

Finance
contextVersion: 1
```

After answering the checkpoint:

```text
Finance
contextVersion: 2
```

The previous conversation history is still preserved.

This allows the system to keep the complete history while treating the new module context separately.

# API Endpoints

Base URL:

```text
http://localhost:8000/api/v1
```

## Module APIs

### Create Module

```http
POST /modules
```

Request body:

```json
{
  "name": "Career"
}
```

The backend generates the module UUID.

---

### Add Question

```http
POST /modules/:moduleId/questions
```

Request body:

```json
{
  "text": "What kind of help are you looking for?",
  "isCheckPoint": false,
  "options": [
    {
      "text": "Backend Development",
      "nextModuleId": "module-uuid",
      "nextQuestionId": "question-uuid"
    }
  ]
}
```

The backend generates the question ID and option IDs.

---

### Update Question

```http
PUT /modules/:moduleId/questions/:questionId
```

Used to update question details and options.

# Conversation APIs

## Start Module

```http
POST /conversation/start/:moduleId
```

Request body:

```json
{
  "userId": "user-001"
}
```

This starts a module for a new user or resumes the user's saved state for that module.

---

## Answer Question

```http
POST /conversation/answer
```

Request body:

```json
{
  "userId": "user-001",
  "questionId": "question-uuid",
  "optionId": "option-uuid"
}
```

The service:

1. Finds the user's conversation.
2. Checks the user's active question.
3. Validates the selected option.
4. Saves the answer in conversation history.
5. Finds the next module and question.
6. Updates the module state.
7. Updates the active state.
8. Increases the context version when the current question is a checkpoint.

---

## Get Current State

```http
GET /conversation/current?userId=user-001
```

Returns the user's current module and question.

Example:

```json
{
  "success": true,
  "data": {
    "moduleId": "module-uuid",
    "currentQuestionId": "question-uuid"
  }
}
```

---

## Get Conversation History

```http
GET /conversation/history?userId=user-001
```

Returns the user's complete conversation history.

---

## Deep Link

```http
GET /conversation/deep-link/:userId/:questionId
```

This handles users opening an old question link.

If the requested question is still the user's current question, it is returned.

If the requested question is old or no longer valid, the user's current valid question is returned instead.

# Example Conversation Flow

A user can move through different modules based on the selected options.

Example:

```text
Career Q1
   │
   ├── Backend Development
   │        ↓
   │     Career Q2
   │        │
   │        └── Node.js
   │               ↓
   │           Finance Q1
   │
   ├── Financial Guidance
   │        ↓
   │     Finance Q1
   │
   └── Health Guidance
            ↓
         Health Q1
```

The user's complete history is maintained even when the user switches modules.

For example:

```text
1. Career Q1 → Backend Development
2. Career Q2 → Node.js
3. Finance Q1 → Continue with Career
```

At the same time, `activeState` only contains the user's current location.

# Setup

## 1. Clone the repository

```bash
git clone <repository-url>
cd wyse-task
```

## 2. Install dependencies

```bash
npm install
```

## 3. Create environment file

Create a `.env` file in the project root:

```env
PORT=8000
MONGO_URI=your_mongodb_connection_string
```

## 4. Start the server

```bash
npm start
```

The server will run on:

```text
http://localhost:8000
```
